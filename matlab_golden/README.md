# matlab_golden

Ground-truth fixtures for testing serdeskit against the official MATLAB
COM3.70 tool (`reference/matlab/COM3.70/`, gitignored — not this
directory) — generated by actually *running* small pieces of MATLAB's own
code, not by reading the source and guessing what it does.

## Why this exists

Reading `com_ieee8023_93a_370.m` and reasoning about what a function
*should* return is unreliable for a ~10,700-line file with several
feature-flag-gated alternate code paths. An earlier debugging pass in this
project's history did exactly that (plus some quick, uncommitted
instrumentation of a live run) and concluded serdeskit's package model
diverged from MATLAB's — a false alarm. The real cause: the tool runs
**two package test cases** (different trace lengths) sequentially within
one process, and that capture wasn't tagged by which case was active, so
it silently compared against an ambiguous/wrong-case snapshot.

The fix is process, not carefulness: never hand-copy a number out of a
MATLAB session into a test. Instead:

1. Extract the exact function(s) under test, verbatim, into `lib/` (see
   below) — never modified, so there's no risk of transcribing a formula
   wrong.
2. Write a small script in `generate/` that calls them with fixed,
   explicit inputs and writes the result to `data/*.csv`.
3. Commit the CSV. It's the golden reference from then on — Python tests
   read it, never MATLAB output pasted by hand.
4. If a script needs live values MATLAB itself computed internally (not
   derivable from a small standalone call — e.g. which package block
   parameters a config resolves to), capture them from an actual run with
   an explicit, unambiguous tag (which package test case, which channel,
   which mode) in the *filename*, not just a variable — exactly the
   discipline that was missing the first time.

## Layout

- `lib/*.m` — functions copied verbatim out of `com_ieee8023_93a_370.m`
  (line ranges noted in each file's own git history / the commit that
  added it), so `generate/` scripts can call them directly. Never edit
  these to "fix" anything — if MATLAB's behavior seems wrong, that's a
  finding to investigate, not a file to patch.
- `generate/*.m` — small scripts, each calling one or two `lib/`
  functions with fixed inputs, writing to `data/`. Re-run these (they're
  fast, seconds each) any time you need to regenerate a CSV or add a new
  case; requires MATLAB + `reference/matlab/COM3.70/` locally.
- `data/*.csv` — committed output. This is what `tests/package/test_*_vs_matlab.py`
  actually reads.

## Adding a new golden fixture

1. Find the function in `com_ieee8023_93a_370.m`, extract it verbatim
   into `lib/<name>.m` (`sed -n '<start>,<end>p'`).
2. Write `generate/gen_<name>.m`: `addpath` to `lib/`, call the function
   with explicit test inputs, write `data/<name>.csv`.
3. Run it, inspect the CSV.
4. Write `tests/package/test_<name>_vs_matlab.py` reading the CSV and
   asserting serdeskit's equivalent matches.
5. If the function needs values only a live run resolves (config-derived
   parameters, not just formula constants): capture them with a filename
   tagged by whatever varies across runs (test case, channel, mode) —
   never assume a single untagged capture reflects the run you think it
   does.
